# Saved logins and permissions

Riot should remember the access you give it. Ordinary workspace work and public-source research do not need a prompt for every action. Each bot keeps its browser sessions, encrypted website logins and remembered site access across restarts.

## Save a login once

In **Bot settings → Files & tools → Saved website logins**, enter the HTTPS website, username/email and password, then choose **Save login**. Ask the bot to sign in. You can also give a directly addressed chat command with labelled fields:

```text
Remember this login and sign in:
site: https://example.com
username: your-username
password: "your password here"
```

Use quotation marks around a password containing spaces. This is a local parsing format, not a promise that arbitrary prose containing a password can be recognized. Quoted emails, blockquotes and code blocks do not save logins or grant access. Use the settings form for unusual passwords or when you want to keep the password out of the chat composer entirely.

The app captures supported login commands before queueing or sending them to the model. The password goes into the existing Windows-protected credential store, separately from SQLite chat/history/memory. The model sees login metadata and an opaque ID, then asks Riot to fill observed fields. Riot checks the bot, saved login, current HTTPS origin and current element references before entering the password locally into the website. The model never needs the saved password as a tool argument. The destination website receives what is entered into its form.

The credential file is updated atomically. If protected storage cannot be updated, Riot reports that the new value is **session only** and never writes a plaintext fallback. It must be entered again after quitting in that failure case. Removing a login deletes its persisted entry even when Windows encryption is unavailable; a deletion failure is reported. Deleting a bot removes its saved logins too. Windows encryption protects stored values; it does not isolate them from software running as your Windows account.

Browser cookies and site storage remain in that bot's separate Chromium profile. Website expiry, logout, MFA and CAPTCHA can still require the website's own verification. Use **Profile & browser → Open browser / Use browser myself** to complete it, then let the bot continue.

## Save a server login

Paste the PuTTY, plink, pscp or psftp command you use with `-pw`, an `sshpass -p` command for ssh, scp or sftp, or an `ssh://user:password@host` address into the chat. Riot recognizes it in your own message before the message is queued, stored or sent to the model, saves the host, port, username and password for that bot in the same Windows-protected credential store, and replaces the password in your message with `[saved password]`. A short notice in the chat confirms the saved server and where it is stored; the login ID and instructions for the model are kept beside your message and sent only to the model. Quoted lines, placeholders such as `<password>` or `$PASS`, and a line Riot already masked are ignored. Pasting the same server and username again with a new password updates the login. Saved server logins are listed under **Bot settings → Files & tools → Saved server logins**, where **Remove login** deletes the stored entry. Deleting a bot removes them too.

The model sees only the login ID, host, port and username. To use a login it asks for **run on server** with the ID and a command. Riot shows the exact command and the server, and runs nothing until you approve. After approval Riot checks that the same login for the same server still exists, then starts PuTTY’s `plink.exe` directly, without a shell, with the saved password. Only plink receives the password, and plink sends it only to the saved host. `-batch` mode refuses an unknown or changed server key instead of asking, so check and accept a new server’s key in PuTTY first. The password is redacted from command output, replies and activity like other stored credentials. The model cannot choose another host for a saved login, and output from the server counts as a private source for later search and site checks.

While plink runs, other programs running as your Windows account can read its command line, which includes the password. That is the same exposure as running the pasted command yourself. An approved command can do anything that server account can.

## Remember website access

Saving a login also grants that bot access to the exact HTTPS website. For another interactive website or a generated destination, a site card offers **Remember & allow**, **This task only**, and **Deny**. Remembered permission includes sharing information with the site, filling forms and clicking controls that can send, publish, pay or delete. Give it to sites you intend the bot to operate. Page text or button labels cannot grant it. The scheme, host and port must match; a subdomain or different port needs its own access.

Remembered access never covers uploads. Each upload names the workspace file, its size and the website, and needs its own approval; the website receives the exact bytes Riot read before asking. Downloads started by a bot’s click or key press are saved into the workspace `Downloads` folder only when file editing is on, never overwrite an existing file, refuse shortcut files and carry the Windows mark of the web. Other downloads are cancelled.

Inspect and remove grants under **Bot settings → Files & tools → Remembered website access**, then save settings. Removing a saved login and revoking site access are separate actions. Revoking access does not log out existing website cookies or cancel work already performed. Stop the task before changing access if you need to prevent another in-flight action.

Public URLs directly supplied by you, and exact URLs found in public web results, can be read without another site prompt. A generated URL can carry private text in its path or query, so a new destination requires access. Once private Riot tool sources have been read, a search query needs access for the service that will actually receive it. Ordinary research sends the query to Tavily (`api.tavily.com`) and, only if that attempt fails, to Firecrawl (`api.firecrawl.dev`). Approval for one does not approve the other. Permission to open a page does not send that address, its query, cookies, or saved logins to a reading service. A link that appeared only on a page in the bot’s browser, which can be signed in, can still be opened there, but sending it to a reading service needs approval for that service. Signed or private addresses, including AWS and Google signed-link query parameters, are not handed to those services or promoted as ordinary results. Each bot can make 40 of these research requests per day, including fallbacks, native `riot_web_search` and `riot_fetch_url`, and a connection check. Account mode also reserves the shared account daily cap in the same step; a refused counter does not spend the other one, and a saved key does not raise the bot limit. The current mode, provider, key, grant, and limits are checked again after address lookup and after any approval wait, immediately before the request is sent. Browser searches still need access for the search site they open. An open browser does not by itself move Automatic research into the browser. These checks reduce unintended sharing. They are not a complete data-loss-prevention system: approved sites, public pages and their redirects can receive requests, queries can contain sensitive material, and source provenance can be incomplete after earlier history/compaction. Native Codex's built-in search and commands follow its own rules; Riot's Web search setting governs `riot_web_search` and `riot_fetch_url`, not Codex's built-in search. See [Web search](web-search.md).

## Local and custom model endpoints

A custom model endpoint is a connection you add in app Settings, not a website grant. Plain `http://` is accepted only for `localhost`, `127.0.0.1`, and `[::1]`; every other endpoint must be `https://` to a public address. The address and its DNS answers are checked in the main process when saved and again before every request, and the connection is pinned to the checked address. Requests for any other origin or path are refused and redirects are not followed. An optional API key stays in the Windows-protected credential store and is sent only to that endpoint. Servers elsewhere on a home or office network are refused for now; how to grant them is an open owner decision. See [local and custom model endpoints](custom-endpoints.md).

## Project files and powerful actions

Riot file tools stay within the bot's working folder. Common credential files, including `.env`, private keys and cloud credential folders, are blocked by default and omitted from file-content searches. If a project requires them, enable **Allow project secrets** once for that working folder. Their contents may then reach the AI connection. Changing folders resets this grant and editing permission in the settings form. Known stored credentials are still redacted from ordinary model text, streamed replies, tool results, activity and chat; source files and exact-byte undo copies are preserved separately. Filename checks and redaction cannot recognize every secret, image or confidential document.

Riot file tools also refuse hard-linked files. A hard link is another name for the same file, and Windows cannot tell Riot where the other names are, so one of them may be outside the working folder or be a credential file such as `.env`. A file with more than one name is refused by reading, editing and Undo, skipped by file searches and Library, and not served to the website checker. The tool reports: “That file has more than one name (a hard link), and another name may be outside the workspace, so Riot Bot did not open or change it. Replace it with an ordinary copy to use it here.” **Allow project secrets** does not lift this. Package managers that hard-link dependency files, such as pnpm under `node_modules`, will see those files refused; inspect them with an approved terminal command if needed. Riot checks the file it actually opened and creates new files exclusively, so a link swapped in after the path checks is still refused. Approved terminal commands and native Codex tools are outside this check.

An API terminal command still requires review of the exact command because it runs with your Windows user's access. A working directory does not contain that shell. Gmail sends keep complete-message review, the same draft claim, and uncertain-send protection. The one exception is a reply rule you explicitly turn on for one bot and its connected mailbox: Riot may send only an exact saved reply to recipients who are listed on that rule and were already mailboxes in that conversation, after the original message is read again and the current rule still allows it, within that rule’s daily limit. Display names, comments, and text Riot could not read do not authorize that send. Every plain-text and HTML version Riot can read has to match the versions saved with the draft. Mail and model output cannot create that exception. Remembering a website does not approve terminal commands or Gmail sends.

Native Codex uses its own Windows sandbox. The installed legacy policy allows broader filesystem reads than Riot's file tools; the **Allow project secrets** switch does not restrict those native reads. Bots are separated in Riot's APIs, but native reads are not a confidentiality boundary between them. See [Codex permissions](codex.md#permissions-and-sessions).

Disk-space checks accept local drives and folders, rejecting network shares, mapped network drives and links into remote locations before the capacity query. Drive classification uses a fixed noninteractive Windows helper; it never executes a model-provided command.

## Development and eventual distribution

`npm run check` runs type checks, tests and the production build. GitHub CI also audits dependencies and uses a pinned, checksum-verified Gitleaks scanner for full history and current files. Dependency updates are proposed weekly. Runtime data, keys and browser profiles are ignored by Git; still inspect what you stage.

`npm run dist:win` creates a local development installer. `npm run dist:win:release` additionally requires configured publisher signing and fails without it. [Electron fuses](https://www.electronjs.org/docs/latest/tutorial/fuses) disable RunAsNode, NODE_OPTIONS, Node CLI inspection and extra file-protocol privileges, and require the main app's integrity-checked ASAR. The optional Chromium installer uses a utility process and replaces only Playwright's known download-helper fork with a worker thread; other fork targets are refused. This compatibility adapter is checked against the locked Playwright layout and must be revalidated on upgrades. On Windows it enables [Node's system CA trust](https://nodejs.org/api/cli.html#node_use_system_ca1) while retaining TLS validation. Unpacked Playwright files are outside the ASAR integrity guarantee; signing and trusted installation permissions still matter.

The project is not being published as part of this work. Choosing a license, enabling a private reporting route and configuring a publisher certificate remain owner decisions for the eventual release. Existing installers predate these changes; do not treat them as hardened builds. [The review](security-review.md) records verification and remaining work.
